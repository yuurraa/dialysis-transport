# APIs and responsive design

The integration adapters define endpoints and contracts but are not implemented. Configure their backend credentials when implementing each integration.

## Responsive web application

Use one React application across phone, tablet and desktop browsers. Patient, caregiver and driver views prioritise stacked cards, next pickup and large actions. The coordinator view uses a wider desktop workspace, adapting to cards on smaller screens. Roles determine access; screen width only changes presentation.

`PageLayout` contains the public landing page. The coordinator dashboard has a separate fluid workspace with its own navigation and account page. Both use responsive spacing. Use compact layouts for personal views and wider layouts for coordinator workflows. Keep text at least 16px, controls at least 44px tall, visible keyboard focus, and readable status labels. Dialogs and maps must fit the viewport. No separate mobile app, desktop app or PWA is needed for this scope.

## OneMap

| Purpose | Endpoint |
| --- | --- |
| Obtain token | `POST https://www.onemap.gov.sg/api/auth/post/getToken` |
| Resolve address/postal code | `GET https://www.onemap.gov.sg/api/common/elastic/search` |
| Baseline driving route | `GET https://www.onemap.gov.sg/api/public/routingsvc/route` |

Register an account and set backend-only `ONEMAP_EMAIL` and `ONEMAP_PASSWORD`. Search and routing use the returned token in `Authorization`. Tokens expire after three days; use the supplied Unix expiry. Search can return an error inside HTTP 200, so validate the body.

Search requests include `searchVal`, `returnGeom=Y`, `getAddrDetails=Y` and `pageNum`. Driving routes use WGS84 `start=latitude,longitude`, `end=latitude,longitude`, `routeType=drive`; normalise `route_geometry`, `total_distance` and `total_time` to the service contract. Traffic adjustment belongs in trip assessment.

For later map rendering, use OneMap's `https://www.onemap.gov.sg/maps/tiles/Default/{z}/{x}/{y}.png` with Leaflet and retain the required OneMap logo and SLA attribution. Basemap tiles do not need API tokens. The map library/component has not been added yet.

Sources: [Authentication](https://www.onemap.gov.sg/apidocs/authentication), [Search token handling](https://www.onemap.gov.sg/apidocs/docs/verifyingsearchapitoken), [Routing](https://www.onemap.gov.sg/apidocs/routing), [Basemap](https://www.onemap.gov.sg/docs/maps/index.html).

## LTA DataMall

Use `TrafficIncidents` and **`v4/TrafficSpeedBands`**, under `https://datamall2.mytransport.sg/ltaodataservice/`. The current user guide is version 6.10, dated 1 October 2026. Register for API access and supply backend-only `LTA_ACCOUNT_KEY` as the `AccountKey` header.

Responses contain `value` arrays. Retrieve complete feeds with 500-record pages and `$skip`. Incidents update about every two minutes, speed bands every five minutes; cache centrally and record freshness. Match observations to the route before adjusting ETA. These feeds do not provide a complete patient-trip ETA. OneMap and traffic assessment must share the five-second response budget; do not fetch an entire traffic feed for every browser viewer.

Source: [Official LTA API user guide, sections 1, 2.18 and 2.19](https://datamall.lta.gov.sg/content/dam/datamall/datasets/LTA_DataMall_API_User_Guide.pdf).

## Google Calendar

Calendar connection is optional and distinct from Supabase login. Enable the Calendar API in a Google Cloud project, configure a web OAuth client and test users, and set backend-only `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and `GOOGLE_CALENDAR_REDIRECT_URI`. The example callback URL reserves a future route; it is not available yet.

Request `calendar.events.owned` for each recipient's own primary calendar. Bind expiring OAuth state to the authenticated user; validate it before exchanging the code. Request offline access and securely store each user's refresh token for later schedule changes. A Google login alone does not grant Calendar access.

Create pickup events with `POST`, update with `PUT`, and remove with `DELETE` under `https://www.googleapis.com/calendar/v3/calendars/primary/events`. Use recipient tokens, RFC3339 start/end times, `Asia/Singapore` and popup reminder overrides. Store event IDs and sync status. Check trip access and stored event ownership; never include treatment details. Calendar failure must not undo a successful trip change.

Sources: [Scopes](https://developers.google.com/workspace/calendar/api/auth), [Web OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [Insert](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert), [Update](https://developers.google.com/workspace/calendar/api/v3/reference/events/update), [Delete](https://developers.google.com/workspace/calendar/api/v3/reference/events/delete).

## Driver location

Location comes from the driver's browser, not OneMap or LTA. `watchDriverLocation` is a small browser boundary: it requires a secure context and permission, returns coordinate/accuracy/time updates and supplies a cleanup function. It is not wired into trip pages or backend reporting yet.

Start only on the assigned active trip after an explicit driver action. Stop on trip end, cancellation, sign-out or leaving the view. Backend authorisation remains required. Browser updates are limited to active, visible documents; do not promise background or locked-phone tracking. If updates stop, display the last-update time and stale-location state.

A phone opening a local development server by LAN IP will need HTTPS for geolocation; desktop localhost is suitable for local testing. Production requires HTTPS.

Sources: [Geolocation standard](https://www.w3.org/TR/geolocation/), [Browser API](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation/watchPosition).


## Dashboard page and overlay format

New dashboard screens must reuse `PageHeading` and `Overlay` from `frontend/src/components/DashboardUI.tsx` and the theme tokens in `frontend/src/styles.css`. Keep one clear page title first, with its optional subheader underneath, and one primary action; use section headings below it. Page subheaders use readable sentence case and muted text; operational headings use the shared sans-serif family and account metadata retains the shared description style. Patient search hints consistently use “Patient name” and “ID”: “Patient name, phone or ID” for the patient list. Coordinator schedule search uses “Patient or schedule details”. Search guidance may specify a full patient ID where required. Patient search actions reserve enough width for the complete search hint and wrap below the heading on narrow screens. Do not duplicate the page name in an eyebrow. Use the shared primary, secondary and destructive control styles rather than adding page-specific button palettes or radii. Action groups use primary first, Cancel/Close next, and Delete last in both visual and keyboard order. Paired actions have equal widths; the Delete shortcut remains compact. Preserve Previous/Next order for pagination and the existing Next/Sign Up, Back, Cancel sequence for signup.

List pages use open layouts with headings and thin record separators, without outer card frames. Short desktop lists end naturally; long desktop lists retain a named, keyboard-focusable bounded scroll region and visible pagination. Each list returns at most 10 records per page. The record count, page count and Previous/Next controls remain fixed at the bottom of the viewport on desktop and mobile. The shared pagination measures its height and visible viewport so content stays clear of the bar; on phones, the Add Schedule button sits above it. At 760px and below, records use natural page scrolling. Patient tables become stacked name-first records on phones, with visible contact, mobility, status and Info controls; the full ID remains in Patient Details. The shared toolbar is ordered Search, Filters, Sort on desktop and mobile. Filters and Sort open separate overlays; Sort uses large radio choices for the field and ascending/descending order, with no native sort dropdown. Patient table header sorting remains available. On phones, the toolbar sticks below the measured header height for the entire list. The desktop header shows Singapore date/time before the theme control. Mobile prioritises the page title and hamburger, theme, notification and account controls; the live clock is hidden on phones.

Use an `Overlay` for add, edit, detail and confirmation flows that can preserve the current page. Its heading remains visible; only the body scrolls. Overlays have no header X button. Edit, filter, sort and confirmation forms also have a persistent action footer. Read-only details use one labelled Close action in the persistent footer. Coordinator Patient Details groups Edit Patient beside Close in that footer; Trip details groups Close and Delete Trip in the same persistent footer row on desktop and mobile. Forms retain their Save/Cancel or Apply/Cancel actions. The navigation drawer also uses a labelled Close control; overlay errors use a labelled Dismiss action. The shared component handles native modal semantics, Escape/backdrop dismissal, focus containment/restoration and background scroll locking. Pass `busy` during mutations to prevent dismissal or duplicate submission; retain inputs on failure. Supply optional footer actions and an optional `onSubmit` rather than embedding another form. Test with long data at desktop and phone widths, a short viewport and enlarged text.

Coordinator My Account uses the same two-column labelled field layout and neutral disabled styling as the patient account, stacking to one column on mobile. Username, Email, Role and Status are read-only, with no edit action. The Patient List title is singular. Its desktop table heading uses 4px vertical padding around the existing 44px sorting controls, reducing the heading height without changing data-row spacing.

Patient My Account edits the existing fields in place. Edit profile switches to Save profile/Cancel, with a subtle rose fill and accent border on editable controls in both themes. Disabled/read-only values keep their neutral appearance; coordinator patient edits highlight only the permitted fields. Save and Cancel keep the same field layout and restore focus to Edit profile after finishing. Failed saves preserve the draft and show an inline alert near the actions; version conflicts require reloading the latest details before retry. Saving disables inputs and actions; inactive profiles remain read-only.

Treatment schedules use one Edit action. For recurring entries, **Apply changes to** distinguishes the entire series from one occurrence. The editor keeps the same responsive height and Save/Cancel/Delete slots in both modes. Delete always removes the entire selected schedule (including its replacements for a recurring series), and its confirmation states this scope explicitly; it does not cancel only the selected unchanged occurrence. One-session editing lists actual dates on the recurring weekday and excludes already replaced occurrences. Series longer than 52 occurrences use a month filter, so any supported year remains reachable without rendering an unbounded list. The selected original session and new date are adjacent; the new date follows the selected session until the user explicitly changes it. Existing schedules do not show a redundant disabled schedule-type control. Single entries display their weekday and date; recurring entries display “Every [weekday]” and a labelled date range. The centre address uses the existing read-only field appearance. Delete is a secondary text action on desktop and a compact, labelled trash control on mobile; Footer actions follow reading order: Save Schedule, Cancel, then Delete. Save and Cancel use equal widths on desktop and mobile; Delete stays compact. Schedule deletion is confirmed inside the same overlay. Deleting a series removes its linked replacements; deleting a replacement restores the original occurrence only if it does not conflict with another session. Treatment deletion does not cancel transport trips.


Overlay mutation errors use the shared `error` / `onDismissError` toast rather than an error paragraph at the bottom of a long form. The toast lives inside the native modal so it remains visible and interactive in the top layer; it is announced as an alert and persists until dismissed, retried or the editor is closed. It floats above the footer without hiding its actions. Schedule validation uses this same path and retains all entered details. Page-load failures keep their persistent unavailable/retry state.


Scheduling choices use the shared `Dropdown` component rather than native select popups whose height cannot be controlled by application CSS. Its list is limited to the available space and at most 35% of the viewport (224px cap), scrolls internally and stays inside the active dialog. Arrow keys, Home/End, typeahead and Enter select options; Escape closes the list before the modal, and Tab continues through the form. Keep the existing bounded centre search for the searchable reference directory.

Recurring cards display a count of rescheduled sessions instead of joining dates into a growing comma-separated paragraph. The count opens a separate Rescheduled sessions overlay, with original and replacement dates in individual entries and a bounded scrolling body. Replacement records remain individually editable from the schedule list.

The coordinator schedule page uses “Treatment Schedule List” / “Schedule Management”, with server-side search over all permitted schedules by patient name or ID plus all fields supported by patient schedule search: centre name, weekday, date and schedule type. Cards show the full patient ID for coordinators and place the schedule type beside the patient name in a wrapping identity row for both roles. Patients also have schedule search by centre name, weekday, date or schedule type, alongside Add Schedule. Both searches trim whitespace and ignore case, apply before pagination, and use 10 records per page with fixed Previous/Next controls shown as spaced `<` and `>` buttons with accessible names. Pagination stays visible during loading, with controls disabled until ready. Related replacement details remain available even when they are on another page. Coordinator schedules remain read-only.

Patient and schedule editors preserve drafts on HTTP 409 version conflicts. They require an explicit reload before retrying; do not silently merge or overwrite a newer record.


Trips reuses `PageHeading`, compact records separated by thin rules, and shared pagination beneath the list. The pagination footer remains pinned to the bottom of the viewport on desktop and mobile. Coordinator status filters use independent checkboxes with counts in the shared filter overlay alongside dates and direction. All statuses are checked by default and after Reset. Deselect statuses to choose a combination (for example Unfilled and At-Risk); at least one remains selected. Selecting every status means no status restriction. They apply together and Cancel discards draft changes. Status selections count as one active filter category. An icon-only Filters button sits beside server search, with a top-right badge counting active status, direction and a date range changed from the default. Hide the badge when no filters are active. The date range appears only in the bounded filter overlay, where date/direction changes apply together. Details opens full route/treatment information in an overlay instead of expanding every list row. Place the status badge directly after Outbound/Return in the heading, followed by patient name, muted ID, the vertical From/To route and separate timing fields. Long addresses wrap and only the body scrolls. Patient Next pickup is a compact summary with its own detail action above the searchable ride list; it does not repeat the full address/details grid. Coordinator schedules have a separate **Generate Trips** action; it opens a compact, flat overlay with the patient name, schedule-type badge, secondary Patient ID, session day/time and dialysis centre. A bounded date window and short hint replace the long source explanation. Outbound-arrival and return-pickup rules appear as two labelled values. Timing values stack on narrow phones. Entered dates remain intact on failure/conflict. Generation errors use the overlay toast. Unfilled and Needs review are distinct signals; treatment-derived arrival deadlines and earliest return pickup must not be labelled as actual pickup times. Patient next pickup remains independent of list filters. Driver and Caregiver placeholders remain until their authorized data paths exist.

Coordinator trip deletion uses a compact destructive shortcut and an explicit single-journey confirmation overlay. Preserve the selected context and error toast on failure; stale versions require reloading before retry. Keep shared primary/Cancel action order, busy dismissal protection and focus restoration.


## Interface identity and colour preferences

The shared interface uses warm Oat/Ink/Mulberry semantic tokens in `styles.css`. A one-click light/dark button is available in public and authenticated headers. `index.html` applies the saved light/dark preference before paint, defaulting to Light when storage is unavailable or a legacy System value is present. OS theme changes do not change the application theme. No photographic or gradient background is loaded into operational screens.

Use modest 5px corners on controls, thin dividers, tabular time values and readable sentence-case supporting text. Operational lists sit directly on the canvas; the next-pickup strip has a single accent edge. Status and schedule-type badges use labelled semantic colours; meaning never relies on colour alone. Trip rows align dates and status beside route/timing on desktop and form a vertical journey on phones. Schedule records align patient identity with treatment day/time and facility on desktop and stack on phones. Trip records separate origin/destination from actual pickup or treatment-derived constraints. Mulberry identifies primary actions; warning and destructive feedback have separate semantic colours and explicit wording. Editorial serif typography is reserved for the public introduction. This design replaces earlier guidance prescribing full-height empty panels, teal surfaces and uppercase subheaders; behaviour, role access and existing workflows remain unchanged.

### List query controls and deployment

All Filter and Sort overlays share a maximum 520px width and use content-fitted height (`fit-content`), capped to the viewport with a 32px margin allowance. Short viewports or enlarged text can scroll the body. On phones (760px and below), they remain centred with the same size caps and a 24px margin allowance; content scrolls when needed. Footer actions share one row and retain their touch targets. Headings and action footers stay visible while only the content scrolls, including on short screens or with enlarged text. Patient, Schedule and Trip filters each include a short explanatory subheader. All filters and sorts apply before pagination and retain existing role/ownership checks. Applying either resets to page 1 and preserves the other choices and search. Cancel, Escape or backdrop dismissal discards draft selections; Reset restores filter or sort defaults in the overlay and Apply commits them. Sort order tooltips and hints describe the selected field (dates/times, text, or the actual category sequence); the toolbar tooltip describes the applied order. Controls remain available for empty/error results. Failed list loads use a shared flat warning state with a short heading, explanation and primary Try again action. Unavailable counts and pagination are hidden until recovery.

### Android dynamic-toolbar verification

Firefox Android has a [reported fixed-position/dynamic-toolbar issue](https://bugzilla.mozilla.org/show_bug.cgi?id=1797964). Our former `visualViewport.offsetTop + height` top positioning added a separate source of displacement to both pagination and the FAB. Native bottom anchoring removes that coordinate dependency; it does not claim to fix browser compositor defects.

The list regression test injects a lagging VisualViewport height and checks footer/FAB spacing through viewport resizing and page scrolling, footer padding changes, final-record action clearance and opening Add Schedule. This is a layout regression simulation, not Android toolbar emulation. On an Android device, check Firefox with its address bar at the top: load a long fixture schedule list with the toolbar expanded, scroll down until collapsed, scroll back up, and repeat near the last record. Repeat in Chrome Android and portrait/landscape. Pagination should sit at the visible bottom; the FAB should remain 16px above it, and final-row Info/Edit actions should scroll clear and remain tappable. Also verify display cutouts/navigation insets and opening/closing the schedule dialog.

At 760px and below, trip records use a compact date/direction/status hierarchy, 16px text and a two-stop pink route timeline. Mobile Firefox pagination also compensates for [Mozilla bug 2057232](https://bugzilla.mozilla.org/show_bug.cgi?id=2057232), where an expanded top toolbar is included in the bottom safe-area inset. A Firefox-only mobile rule subtracts `100lvh - 100dvh` from the reported inset, with a 12px padding floor. Other engines keep the native inset. Direct inspection on the connected Android Firefox page with the URL bar expanded found a 47.25px bottom padding before the correction; afterwards pagination measured 68px high with 12px bottom padding, its bottom matched the visible viewport, and the FAB retained a 16px gap above it. No scrolling was automated or browser tests run; collapsed-toolbar and cutout/orientation behaviour still require manual device review.
