## OneMap

| Purpose | Endpoint |
| --- | --- |
| Obtain token | `POST https://www.onemap.gov.sg/api/auth/post/getToken` |
| Resolve address/postal code | `GET https://www.onemap.gov.sg/api/common/elastic/search` |
| Baseline driving route | `GET https://www.onemap.gov.sg/api/public/routingsvc/route` |

Register an account and set backend-only `ONEMAP_EMAIL` and `ONEMAP_PASSWORD`. Search and routing use the returned token in `Authorization`. Use the expiry returned by the provider rather than assuming a fixed token lifetime. Search can return an error inside HTTP 200, so validate the body.

Search requests include `searchVal`, `returnGeom=Y`, `getAddrDetails=Y` and `pageNum`. Driving routes use WGS84 `start=latitude,longitude`, `end=latitude,longitude`, `routeType=drive`; normalise `route_geometry`, `total_distance` and `total_time` to the service contract. Traffic adjustment belongs in trip assessment.

The in-app Leaflet map uses OneMap's `https://www.onemap.gov.sg/maps/tiles/Default/{z}/{x}/{y}.png` with Leaflet, retaining the required OneMap logo and SLA attribution. Basemap tiles do not need API tokens. Map panning/tile requests use OneMap's documented Singapore bounds, and tiles use anonymous CORS requests (the provider supports `Access-Control-Allow-Origin: *`) without third-party cookies. Some out-of-coverage URLs return HTTP 200 with empty PNG bodies; these are provider image failures, separate from route/traffic API processing. Trip details renders the route and pickup/destination markers; provider failure leaves a textual route with Retry.

Sources: [Authentication](https://www.onemap.gov.sg/apidocs/authentication), [Search token handling](https://www.onemap.gov.sg/apidocs/docs/verifyingsearchapitoken), [Routing](https://www.onemap.gov.sg/apidocs/routing), [Basemap](https://www.onemap.gov.sg/docs/maps/index.html).

## LTA DataMall

Use `TrafficIncidents` and **`v4/TrafficSpeedBands`**, under `https://datamall2.mytransport.sg/ltaodataservice/`. Confirm the current endpoint version against the official guide before implementation. Register for API access and supply backend-only `LTA_ACCOUNT_KEY` as the `AccountKey` header.

The backend adapter validates every record before publishing a complete feed, shares concurrent refreshes, caches incidents for two minutes and speed bands for five minutes, and reports provider failures without returning stale or partial data as success. A cancelled viewer does not cancel another viewer’s refresh. Individual feed timestamps are retained; these are retrieval times, not provider observation times. The authorised trip traffic endpoint exposes near-departure/active advisory assessments, speed coverage, feed timestamps and nearby map observations; see [current traffic assessment](development.md#current-traffic-assessment) for the estimation limits.

Responses contain `value` arrays. Retrieve complete feeds with 500-record pages and `$skip`. Incidents update about every two minutes, speed bands every five minutes; cache centrally and record freshness. Match observations to the route before adjusting ETA. These feeds do not provide a complete patient-trip ETA. OneMap planning requests retain a five-second response budget; route traffic reads allow twelve seconds for shared feed refreshes. Complete speed-feed refreshes have a twenty-second internal deadline, fetch up to eight 500-row pages concurrently and remain shared/cached across viewers. The defensive cap is 200,000 raw rows; reaching it without an end page remains a failure. Band 0 with empty speed fields is treated as no observation and excluded from speed coverage, never as stopped/clear traffic. Do not fetch an entire traffic feed separately for every browser viewer.

Source: [Official LTA API user guide, sections 1, 2.18 and 2.19](https://datamall.lta.gov.sg/content/dam/datamall/datasets/LTA_DataMall_API_User_Guide.pdf).

## Google Calendar

UC-13 is implemented locally for active **Patients** and **Caregivers**. Calendar connection is optional and separate from Supabase login. Each recipient connects their own primary calendar from **My Account → Google Calendar**. The calendar icon in Trip details offers **Add to Google Calendar** for any visible trip, including unassigned and past trips. A small dot indicates that the recipient has not opted into an event. Opening the popup never creates one. Without a confirmed pickup time the event is all-day on the trip’s date; once a pickup is set, an existing event updates to that time. The popup previews the event and date/time; notifications are optional (None by default, or 15/30 minutes, 1/2 hours or 1 day before pickup). Saved events can be updated or removed. Caregivers can only add reminders for currently linked active patients, to the caregiver's own calendar. Drivers, coordinators and demo identities/trips cannot connect or create real reminders.

### Setup and deployment

1. Apply the updated `database/schema.sql` yourself before deploying both app layers. No seed rerun is needed. No hosted changes have been applied by the agent.
2. In Google Cloud, enable **Google Calendar API**, configure the OAuth consent screen, and add the patient/caregiver Google accounts as test users while the app is in Testing. Add the `https://www.googleapis.com/auth/calendar.events.owned` scope. The separate consent also requests `openid` to bind the connection to a stable Google account; reconnecting must use that same Google account until it is disconnected. External Testing grants with Calendar scopes may expire after seven days; reconnect when requested.
3. Configure a **Web application** OAuth client. Register the exact local callback `http://localhost:3000/api/calendar/callback` and deployed callback `https://dialysis-transport-api.onrender.com/api/calendar/callback` as authorised redirect URIs. This callback is separate from Supabase's Google sign-in callback. The same client can be used only if both callbacks are registered.
4. Set backend-only `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_CALENDAR_REDIRECT_URI` (the callback for that environment), and `CALENDAR_TOKEN_ENCRYPTION_KEY` (32 random bytes as 64 hex characters). Generate the key locally with `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`. Keep it stable, backed up securely, and consistent across backend instances using the same database; losing/changing it makes stored grants unreadable. Never place secrets in frontend settings or chat. `SUPABASE_SECRET_KEY` is also required; `FRONTEND_ORIGIN` supplies the fixed return address.
5. Restart the backend. Missing Calendar settings leave the integration unavailable without blocking login or trips. Reminder syncing starts only with complete settings and outside `NODE_ENV=test`.

### Security and synchronisation

The backend requests offline consent with expiring, single-use OAuth state and PKCE. Callback codes/tokens never reach frontend state or redirect query strings. After consent, a fresh five-minute opaque ticket returns to My Account; a protected confirmation request must come from the same app account that started the connection before encrypted tokens are attached. This prevents linking a grant to another signed-in account. Google’s stable subject identifier binds subsequent reconnects to the original calendar owner; switching Google accounts requires disconnecting first. Access and refresh tokens are encrypted using AES-256-GCM before storage. Calendar tables enable RLS and deny all browser roles; only the service identity reads credentials. User reminder writes additionally enforce ownership/link access in the database. Connection versions prevent an old consent callback from restoring a disconnected grant.

Events contain only **Transport pickup**, pickup/destination addresses, journey times and an optional popup notification. No patient name, medical details, treatment time, contact information or live location is sent. Google sign-in grants no Calendar access. The integration does not create calendar events until the recipient explicitly opts in.

Trip timing/date/address changes update opted-in events; unassignment changes an existing event back to all-day. Cancellation, deletion, account inactivation and caregiver unlinking queue removal. A recipient may explicitly add a cancelled trip again afterwards as a labelled cancelled event; cancellation itself never creates one. Completed trips retain their events. Synchronisation runs every 30 seconds in batches of five, using database leases, revision checks, stable event IDs and bounded retries. Google failures never undo a successful trip operation. Quota/network errors retry; revoked grants require reconnecting. Google may retain deleted event IDs, so a new ID is saved when restoring an event after removal. If permission was already revoked, the app can forget the connection but cannot guarantee removal of events left in Google; users can remove those manually.

Disconnect first queues removal of app-owned events, then revokes the grant and clears stored credentials. Cleanup is leased and finalised atomically; a credential-free connection record retains its increasing version so a delayed consent callback cannot revive an old connection. Other calendar events are untouched. It can remain pending while Google is unavailable. Do not share one database between local and deployed Calendar OAuth clients with different client credentials; refresh grants belong to the client that issued them.

### Verification

Tests have been extended in existing backend, database and browser cases; **they have not been run**. Run `npm test` yourself after installing dependencies. Live verification requires your Google OAuth credentials: connect as a patient, add a reminder, move/cancel its trip and check Calendar, reconnect after revocation, and repeat for a linked caregiver. Confirm unlinking removes the caregiver's opted-in event and neither driver nor coordinator can access the endpoints. Do not run these checks with actual patient records.

Sources: [Scopes](https://developers.google.com/workspace/calendar/api/auth), [Web OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [Insert](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert), [Update](https://developers.google.com/workspace/calendar/api/v3/reference/events/update), [Delete](https://developers.google.com/workspace/calendar/api/v3/reference/events/delete).

## Driver location

Location comes from the driver's browser, not OneMap or LTA. `watchDriverLocation` is a small browser boundary: it requires a secure context and permission, returns coordinate/accuracy/time updates and supplies a cleanup function. It is wired to the assigned active-trip sharing controls and backend location endpoint.

Start only on the assigned active trip after an explicit driver action. Stop on trip end, cancellation, sign-out or leaving the view. Backend authorisation remains required. Browser updates are limited to active, visible documents; do not promise background or locked-phone tracking. If updates stop, display the last-update time and stale-location state.

A phone opening a local development server by LAN IP will need HTTPS for geolocation; desktop localhost is suitable for local testing. Production requires HTTPS.

Sources: [Geolocation standard](https://www.w3.org/TR/geolocation/), [Browser API](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation/watchPosition).
