# Development and deployment

## Local development

Use Node.js 24 and run the root commands listed in the [README](../README.md). Copy `frontend/.env.example` to `frontend/.env.local` and `backend/.env.example` to `backend/.env`, then fill in the shared Supabase URL and publishable key. Complete the [authentication setup](authentication.md) before testing signup.

| Setting | Local | Render |
| --- | --- | --- |
| Frontend `VITE_API_URL` | Empty; Vite proxies `/api` to port 3000 | Backend HTTPS origin, without `/api` |
| Backend `FRONTEND_ORIGIN` | `http://localhost:5173` | Frontend HTTPS origin |
| Backend `PORT` | `3000` | Supplied by Render |

Keep actual credentials in local environment files and Render settings. Commit placeholders in `.env.example`. Restart local services after changing environment values; rebuild the frontend after changing Vite variables.

Vite listens on port 5173 on all network interfaces. For phone testing, use its printed Network URL on the same Wi-Fi. Google login and browser location on a phone need HTTPS; use the deployed site for those checks.

## Render deployment

Use the same repository and branch for both services. Set Root Directory to the folder containing the root `package.json` and lockfile, such as `dialysis-transport-app`; leave it blank if those files are at the repository root.

| Setting | Frontend Static Site | Backend Web Service |
| --- | --- | --- |
| Build | `npm ci --include=dev && npm run build --workspace frontend` | `npm ci --include=dev && npm run build --workspace backend` |
| Publish directory | `frontend/dist` | N/A |
| Start | N/A | `npm run start --workspace backend` |
| Health check | N/A | `/api/health` |

Set Node.js 24 for both builds. Supply the frontend's `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`, and the backend's `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`, alongside the environment settings above.

On the Static Site, add a **Rewrite** from `/*` to `/index.html` so `/auth/callback`, `/dashboard/trips`, `/dashboard/account` and `/dashboard/patients` load the application on direct visits and refresh. Configure the deployed callback in Supabase as described in [Authentication](authentication.md).

## Tests

The shared budget is approximately 70 tests across frontend, backend and database, not 70 per layer. Current source counts are 19 + 17 + 23 = 59 (including the optional concurrency test); see the README for scope and allocation. Reserve the remaining budget for unimplemented features, and replace duplicate or low-value coverage before adding cases.

Run `npm test` after installing dependencies. It runs:

- Disposable PostgreSQL tests for SQL functions, RLS, role restrictions and database updates.
- Backend HTTP tests for account requests and CORS, including actual backend startup.
- A small browser suite for login/signup, editing, driver review/availability, trips and sign-out.

Tests use fictional identities and do not connect to the hosted Supabase project. Real Google consent and Render configuration still need checking on the deployed app.

The normal database suite uses a single-session disposable engine. To verify real concurrent writes, opt into the additional integration test against a disposable **local PostgreSQL cluster** with the `anon` and `authenticated` roles already created. The local OS database user must be able to create/drop databases. Set `PG_CONCURRENCY_BIN` to an absolute `psql` executable path, `PG_CONCURRENCY_SOCKET` to its live Unix socket directory, and optionally `PG_CONCURRENCY_PORT` (default `5432`), then run:

```bash
node --test --test-name-pattern='real PostgreSQL' database/tests/accounts.test.mjs
```

This test creates and drops its own database containing fictional fixtures. It verifies actual lock waits between independent connections for overlapping inserts, duplicate trip generation, trip deletion/restoration, and stale patient-status updates. Inherited PostgreSQL connection settings are removed and TCP/remote connection targets are rejected. Without the opt-in variables, this integration test is skipped; ordinary database tests alone do not prove concurrent behavior.

Windows browser tests use Microsoft Edge. On other platforms, install Chromium with `npm exec --workspace frontend -- playwright install chromium`; Linux may need Playwright system dependencies. The test frontend uses port 5199.

## Troubleshooting

- **Google login succeeds but signup/account lookup fails:** inspect `/api/auth/me` in the browser Network panel. Check backend availability, `VITE_API_URL` and `FRONTEND_ORIGIN`. CORS must match the frontend's scheme, hostname and port; the backend normalizes trailing slashes.
- **Local `/api/auth/me` returns 401:** the local backend could not validate the saved Supabase session. The app clears it and returns to Google sign-in. If fresh login still fails, compare the frontend/backend Supabase project settings and check the backend's provider error code. Render deployments do not affect requests through the local Vite proxy.
- **Auth user exists but no account row:** the application row is created after the user submits Username and Role. A failed account lookup can block that form.
- **Account lookup unavailable on first visit:** Render's free backend service may be starting. The account panel retries automatically and shows periodic loading reminders.
- **Health reports OK but registration fails:** `/api/health` checks process liveness only. Inspect the account request and confirm the account SQL is installed in the same Supabase project used by both services.

Saved schedules have Info and an edit icon. The edit icon submits a change request; it does not update the saved schedule directly.

The policy is unconditional. `POST /api/schedules` remains available to active patients for new schedules; `PATCH` and `DELETE /api/schedules/:id` reject direct changes with HTTP 403. Creation rejects replacement/rescheduling fields. Drivers and Caregivers have no treatment access. Coordinators retain their existing schedule read view and manual/automatic trip-generation controls. Patients can request edits, deletion, or rescheduling one recurring occurrence. A reason is required, and only one pending request is allowed per linked schedule series. Patients may withdraw a pending request. Coordinators inspect the current schedule and proposal, then approve or reject; rejection requires a reason. Pending and rejected requests appear on schedule rows.

Reapply `database/schema.sql` and deploy backend/frontend together. Authenticated schedule UPDATE/DELETE and the public/private `update_my_treatment` and `delete_my_treatment` RPCs are revoked. Replacement-column INSERT privileges are explicitly revoked on upgrades, and the INSERT policy only accepts independent entries. Existing schedules and generated trips are preserved. Owner-only internal mutation functions and replacement metadata support the controlled approval transaction; they are not client APIs. The new `treatment_change_requests` table retains request/review snapshots, including after schedule deletion. RLS allows active owners and coordinators to read requests; direct request writes are revoked.

The request endpoints are `POST /api/schedules/:id/change-requests`, `GET /api/schedules/:id/change-request`, `PATCH /api/schedules/change-requests/:id/withdraw` and coordinator-only `PATCH /api/schedules/change-requests/:id/review`. Requests carry the schedule version; withdrawal and review carry the request version. Approval rechecks both the selected schedule and root versions and validates the proposal again. Stale decisions return 409 and require reloading; failed approvals leave the request pending and roll back all changes.

Approval locks the patient, root schedule, selected schedule and request consistently. It applies the schedule change and reconciles affected future unfilled trips in one transaction, preserving past trips and deliberate deletion tombstones. The `trips.schedule_change_cancelled` flag distinguishes obsolete occurrences from deliberate deletions, allowing the former to return when a later approved change restores the occurrence. Rescheduling keeps journey identities where possible; deleting a replacement restores the original occurrence. Generated future trips that no longer correspond to an occurrence are retired with an audit event. An existing generated range is reconciled even with auto-generation off; approval does not manufacture trips for schedules that have neither generated trips nor auto-generation enabled. Affected assigned journeys are shown before approval and require explicit acknowledgement. Approval rechecks a token of their IDs/versions, releases only changed assignments with audit history, and preserves unaffected assignments. Affected journeys whose pickup has started still block approval. Disabling auto-generation still leaves existing trips intact. Keep request records and protected functions when rolling back application code; older clients must not regain direct mutation permissions.

- **Recurring:** one weekday, time range and centre, repeating weekly between inclusive effective dates.
- **Single Session:** one specific date, time range and centre, independent of recurring entries.
- **Existing rescheduled sessions:** remain readable and are respected by manual/automatic generation. Their original occurrences remain excluded so journeys are not duplicated. New replacements and changes to existing ones require an approved request.

All times are Singapore local time. Only same-day sessions are supported. The application records appointments already arranged with a centre; it does not book clinical capacity or confirm transport. Centre selection uses bounded searchable results and an always-present read-only address field. Single sessions and recurring entries have distinct creation fields. Cancelling, Escape or backdrop dismissal before confirmation sends no creation request.

Patient-profile edits remain version checked through `save_my_patient` or coordinator `save_patient`. Schedule versions protect trip generation and approval decisions; changing a coordinator's auto-generation preference does not modify the treatment snapshot version.

`GET /api/schedules?page=1&search=...` now calls the RLS-respecting `list_treatments` function. Search is applied before pagination (10 records per page); the response includes `total`, `page`, `pageSize` and the related schedule `context` needed for exception counts, history across pages. Search supports the existing centre/day/date/type fields, plus patient name/ID for coordinators. Sorting remains effective start date, then schedule ID.

New or updated treatment dates must be within AD 0001-01-01 through 9999-12-31, and the selected weekday must occur within the date range. The database enforces these rules even for direct inserts. Date/occurrence constraints use `NOT VALID` during upgrade to preserve existing records; they still enforce every new insert/update. Any historical invalid records require explicit correction rather than automatic deletion. The list displays unsupported legacy dates as “Invalid date” instead of failing to render. Keep these constraints, version columns and protected write functions when rolling back application code; old clients without versions must reload/update rather than silently overwrite newer data.

## Initial trip generation

Reapply `database/schema.sql` and deploy the backend/frontend together. This adds RLS-protected `trips` and `trip_history` tables, `generate_treatment_trips(target, from_date, until_date, expected_version)` and `list_trips(page_no, from_date, until_date, status_filter, search_text, direction_filter)`. No service-role key is required. Authenticated direct INSERT/UPDATE/DELETE on operational tables is revoked. Source UUIDs are retained as history even after a treatment schedule is deleted.

`POST /api/trips/generate` accepts only `schedule_id`, `from_date`, `until_date` and the source `version`; active Coordinators only. Windows are inclusive, start no earlier than Singapore today, and end no later than the fourth Sunday (current week plus three). Generation locks Patient → Schedule → Trips, rechecks the source version and creates/refreshes snapshots atomically. A unique root-occurrence/direction key prevents duplicate pairs, including concurrent identical requests. The response reports `created`, `updated` (including restored journeys), `unchanged`, `skipped` (retained as zero for response compatibility) and `total`. Recurring generation excludes replaced originals and includes replacements whose actual dates fall in the chosen range. Already-started sessions are skipped. Buffer overflow beyond the supported year range is rejected.

`GET /api/trips` accepts `page`, `from`, `until`, `status`, `search` and `direction`; the default starts on Singapore today with no end date. Omit `until` or send an empty value for an open-ended view (`until_date=NULL` in the database). An explicit end date must be on or after the start; list views have no 90-day span cap. Trip generation is restricted to the shared four-calendar-week planning window. Date, direction and literal, case-insensitive search filtering precede status filtering and pagination (25 journeys/page). Search covers route/centre text, weekday, date, times, journey direction, status, pickup-pending/review labels, plus patient name/ID for Coordinators. Search is limited to 100 characters. Counts reflect the active date/search/direction scope before status filtering; Next pickup remains independent of list filters. The response includes `trips`, `total`, `page`, `pageSize`, range-scoped category `counts` and the next authorized pending journey independently of the selected list window. Active Patients read only owned active-profile trips; active Coordinators read permitted operational trips. Active Drivers read only their currently assigned, nondeleted trips through RLS; unassignment immediately removes that access. Caregivers remain denied pending verified links.

Each session produces two Unfilled journeys. Outbound `arrival_by` is treatment start minus 15 minutes; return `pickup_not_before` is treatment end plus 15 minutes, in `Asia/Singapore`. `pickup_at` remains null until a coordinator explicitly assigns a driver and a pickup time. Operational risk, confirmation, cancellation, tracking and calendars remain separate future changes.

Requirement changes mark affected current/future unfilled journeys `review_required` and append history. Regeneration refreshes matching journey snapshots and clears that flag; it does not silently delete old journeys whose occurrences no longer exist. Those remain for explicit coordinator review until cancellation/recovery is implemented. Return journeys remain pending through their Singapore pickup-ready day, including the treatment-end buffer. Database tests cover buffers, recurrence exceptions, retries, source/profile changes, private history and pagination. The opt-in PostgreSQL concurrency test also verifies concurrent generation and generation/source-edit races.


Coordinator **Delete Trip** removes one unassigned journey from normal lists, counts and next pickup. `DELETE /api/trips/:id` requires exactly `{version}` and calls `delete_trip(target, expected_version)`. It checks the active coordinator role, locks Patient → Trip, verifies the current version, records `deleted_at` and a durable `deleted` history event. The row and its unique occurrence key remain for audit. Explicitly generating the same future session restores deleted journeys using their existing IDs and current treatment/patient details, clears `deleted_at`, increments their versions and records a `restored` history event alongside the original deletion. Unchanged surviving journeys remain untouched, and repeated generation creates no duplicates. Reapply `database/schema.sql` to enable restoration in an existing database. Patients cannot delete trips; direct table writes remain revoked. Source/profile changes and generation refreshes increment trip versions, so a stale delete returns HTTP 409 with an explicit reload action. This does not alter the treatment schedule or automatically delete the other journey in the session.
